菜单同时包含「基础档案 → 编码规则」和「仓库管理 → 供应商回填」。客户门户采用专用组件，运营商配置继续保留供应商类型、接口类别、适配器与自定义地址。

## 数据库入口

统一使用 `python3 database/migrate.py --user root`；加 `--check` 只读检查计划，新装演示库加 `--demo`。默认库为 `yunshu`，支持指定其他数据库进行隔离验证。执行前停止业务写入并备份；脚本不会修改现有账号密码。

| 顺序 | 步骤 | 脚本 / 行为 |
| --- | --- | --- |
| 1 | core | 空库执行 01，已有完整结构登记接管；02 只在新装且显式指定 --demo 时执行 |
| 2 | prototype | 旧库执行 05-upgrade 兼容结构及历史 ID；已存在编码规则的完整新版库只登记接管 |
| 3 | code-rules | 05-code-rules，只执行一次，保留旧展示编码并新增自动发号 |
| 4 | page-fields | 06-page-fields，只执行一次，JSON 档案转业务列，补齐单据行卡表及同步触发器 |
| 5 | schema-comments | 07-schema-comments |
| 6 | product-categories | 08-product-categories，保留原分类 ID，回填上下级、商品归属及引用次数 |
| 7 | supplier-inbound | 06-supplier-inbound，补齐供应商字段、队列字段及索引，保留已存在的配置 |

不能依靠 05、06 文件名前缀判断顺序。历史 03 只供原始新装，不纳入当前执行链；04 仅为可选演示订单。旧版 05-upgrade 在发现编码规则表后会主动停止，防止覆盖新的门户视图。

`schema_migration` 保存版本、原文件校验和、started/done 状态与完成时间。迁移使用同一 MySQL 会话持有命名锁；重复执行跳过已完成步骤。脚本检测到部分结构、校验和变化或未完成记录时停止。MySQL 的 DDL 不会整体回滚：发生中断后先核查报错和备份，不要直接删迁移记录并重跑。

- 后端 `mvn test`：11 项通过，包括供应商路由、CTBOSS 适配器和回填逻辑；前端 `npm run build`：TypeScript 检查和构建通过。

- 本地真实数据库备份在隔离库升级成功；原有 3 个账户及密码哈希完全一致，原有 2 张订单及明细保留。原始订单和商品行保留；旧库缺失的两条 `order_line_extra` 扩展记录已补齐（默认税率 13%，备注为空），`portal_field` 按 GitHub 功能新增两条 `order_code` 可见字段配置，其余原业务表行数保持一致。
- HTTP 接口验证通过：ERP 登录、客户门户登录及错误入口拒绝、编码规则、三级分类创建与引用次数、被引用分类拒绝删除、商品业务字段、供应商配置、采购创建/提交/审批、采购入库提交/审核、IDENTITY 回填任务、客户目录和跨角色接口权限。
- 入库接口验证使用禁用的模拟供应商账号，没有访问真实运营商。真实供应商网络、凭据和生产返回字段仍需有相应账号时联调。

数据库测试会创建随机 `yunshu_mtest_*` 临时库并在结束后删除。HTTP 流程与真实备份升级在独立测试库执行，不向本地业务库写入测试订单、分类或账户。
